# 现代化 ECMAScript

选择同时满足“规范稳定”和“对目标项目的真实运行环境安全”的最新语言能力。TC39 阶段、TypeScript target 和运行时版本回答的是不同问题，不要把它们合并成一个兼容性结论。

## 按需读取 TC39 Atlas

把 TC39 Atlas 作为本产品提案阶段、状态、版本元数据、双语 README 和提案速览的权威入口：

- 索引：`https://bosens-china.github.io/tc39-atlas/llms.txt`

先读取这一份索引，再根据任务需要获取一个或多个提案 Markdown 页面。索引已提供链接时，不要自行推导提案 URL。

Atlas 描述规范成熟度，不代表 TypeScript、打包器、Node、浏览器或 WebView 的支持情况。兼容性决策依赖这些技术时，查阅与目标版本匹配的官方文档。

## 定位目标项目

从用户指定的文件或包开始。优先使用仓库证据，不凭假设决策；只在存在多个合理目标且选择会实质改变结果时停下询问。

对于单包仓库：

1. 找到仓库根目录，读取 `package.json`、锁文件、脚本和适用的 Agent 指令。
2. 读取最近的 `tsconfig*.json` 与相关构建配置，例如 `vite.config.*`、`webpack.config.*`、Babel、SWC 或框架配置。
3. 检查 `engines`、`.nvmrc`、`.node-version`、Volta 或 mise 设置、Dockerfile、CI 工作流和部署配置等运行时声明。
4. 把当前终端的 `node -v` 只视为本地证据，不把它当作生产运行时证明。

对于 monorepo：

1. 通过 `pnpm-workspace.yaml`、包管理器的 `workspaces`、`turbo.json`、`nx.json`、`lerna.json` 或仓库自身约定识别 workspace。
2. 通过最近的包清单与导入、构建关系，把请求的文件或能力映射到所属应用或包。
3. 读取根配置默认值和目标包覆盖值，包括被继承的 TypeScript 配置与共享构建预设。
4. 追踪目标到它的消费者或部署入口。仅源码包继承所有相关消费者的兼容性要求；已发布库必须遵守声明的消费者基线。
5. 如果多个应用以不兼容的目标消费同一份代码，汇报冲突并询问哪些消费者在本次范围内。

这些文件名只是常见查找线索，不是封闭的框架矩阵。当仓库实际命令、配置继承和部署拓扑不同时，跟随真实结构。

## 识别所有执行面

选择能力前，先对代码分类：

- 由打包器转换的浏览器源码。
- 由 Node.js 直接执行的服务器、SSR、构建配置、迁移或脚本。
- 由测试运行器及其 Node 版本执行的测试代码。
- 在仓库外被消费的已发布库产物。
- 同时进入上述多个环境的共享源码。

为每个范围内的执行面记录 TypeScript/解析器版本、源码能力、生产转换目标、运行时基线和 polyfill 策略。开发环境成功不能单独证明生产兼容性。

## 通过兼容性门槛

按以下顺序评估候选能力：

1. **规范成熟度**：Stage 4 可以继续兼容性检查。Stage 3 必须获得用户明确同意，并提示它仍属实验能力。不要为生产现代化推荐不活跃、已撤回或更低阶段的提案。
2. **解析器与类型系统**：确认已安装的 TypeScript、Lint 解析器、测试转换器和构建转换器理解该能力及其当前语义。
3. **产物与构建**：确认真实生产流程会保留该语法，或能安全转换它。在 Vite 项目中，区分 TypeScript 的 `target` 与 Vite 生产构建的 `build.target`。
4. **运行时**：确认被保留语法和内置 API 的原生支持。语法转换不会自动填充 API；`lib` 类型声明也不证明运行时可用。
5. **兼容性契约**：除非用户明确选择提高基线，否则保留已声明的 Node engines、浏览器目标、库消费者和部署基线。

独立描述两个值：

- **源码能力范围**：例如“Stage 4，截至 ES2024”。
- **产物或运行时基线**：例如“浏览器产物 ES2020，Node.js 20”。

不要只说“启用 ES2024”。源代码可以使用 ES2024 能力，而打包器同时输出更旧的目标。

## 自动决定或集中询问

当仓库证据一致，且候选能力已达 Stage 4、所有相关解析器都能理解、可被安全转换或已获得原生支持，并且不需要改变依赖、polyfill、运行时或公开兼容性时，可以不询问直接继续。

出现以下情况时暂停并询问用户：

- 运行时或浏览器目标缺失、冲突或含糊。
- 存在多个合理的应用或消费者目标。
- 公开库的消费者基线未知。
- 采用该能力需要 polyfill、构建变更、依赖升级或提高 Node/浏览器基线。
- 转换器无法安全降级该能力。
- 该能力处于 Stage 3，或存在装饰器这类相互竞争的旧语义。

询问之前先完成所有安全的自动发现。在一个简洁问题中给出检测到的环境、确切的不确定项、可行选项、各自影响和推荐选择。把相关不确定项合并询问，不要每个能力打断一次。

默认建议是保持当前兼容性基线，只使用已在该基线内安全的能力。

## 修改前汇报

自动解决或用户做出选择后，编辑代码前先汇报计划：

```text
ECMAScript 现代化已准备开始。
- 范围：<应用/包与执行面>
- 源码能力：<Stage 4，截至 ES20xx>
- 产物/运行时基线：<浏览器目标与 Node 版本>
- 策略：<原生支持、语法转换、已批准的 polyfill>
- 包含：<能力类型或候选项>
- 排除：<实验性或不兼容项>
- 基线变更：<无，或已获批准的变更>
```

此时使用“计划”或“准备开始”；后续审查仍可能发现没有值得替换的写法。

## 保守地应用变更

用户只要求分析时，只给出建议。用户要求现代化或实现时，再修改代码。

- 优先选择减少代码或明确意图，且不改变可观察行为的变更。
- 不要只为使用更新语法而提高 engines、浏览器目标、TypeScript、构建工具或依赖版本。
- 分开处理语法、内置 API 和语义型提案；它们的转换与运行时要求不同。
- 保留项目风格和公开 API 行为。
- 只在不写注释就难以理解兼容性决策时添加注释。

根据变更风险，运行目标包已有的格式检查、类型检查、相关测试和生产构建。对于 monorepo，验证受影响的消费者，不要没有理由地运行无关 workspace。

## 用证据完成汇报

汇报：

- 检测到的目标项目与执行环境。
- 实际采用的能力及其 TC39 阶段或 ECMAScript 版本。
- 被跳过的候选能力与具体兼容性原因。
- 是否改变了任何兼容性基线。
- 已完成的命令和检查，包括失败项或未验证的消费者。

不要声称 Stage 4、类型检查成功或开发服务器运行成功就能单独证明运行时兼容性。
